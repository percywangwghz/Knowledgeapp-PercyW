# 一级投研知识库 · 前端重构设计说明书 v2

> 用途：本文件不是设计理念说明，而是一份可以直接交给 Kimi / Coding Agent 执行的前端重构规格书。
>
> 设计目标：在不破坏现有知识库数据结构、AI 后台任务、写回审批、API 持久化等工程机制的前提下，重新设计整个前端的信息架构、页面布局、阅读体验和交互逻辑。
>
> 核心定位：**Personal Investment Research Workspace / 一级投资研究工作台**。
>
> 设计关键词：Calm / Restrained / Editorial / Research / Precise / Quietly Designed。

---

# 0. 重构目标

当前产品已经具备比较完整的功能体系：静态站负责浏览、搜索、阅读；Streamlit 负责 AI 评审、Thesis Battle、Investment Radar、文件归档和知识库写回。现有工程本身没有必要推倒重来，真正需要重构的是“这些能力如何被组织起来”。

本次重构不以“做一个漂亮 Dashboard”为目标，而是将产品从“知识库 + 若干 AI 功能”升级成一个长期可用的研究工作环境。用户打开产品之后，不应该首先看到大量功能按钮，而应该首先理解：我在哪里、最近发生了什么、当前正在研究什么、下一步可以做什么。

最终体验应达到三个标准：第一，连续阅读 1–2 小时不会疲劳；第二，文档、行业、项目、变量、主题之间可以低摩擦跳转；第三，AI 能力始终作为研究助手存在，而不是抢占知识内容本身的视觉中心。

现有工程约束必须保留：后台 AI 任务、job 文件、自愈和中断恢复、Preview → Human Approval 写回、API Key 本地持久化、AI 成本记录、VS Code 打开源文件、现有 9 类知识库体系以及 tracks / status 归一逻辑。两套前端继续保持 Static = Read / Search / Browse，Streamlit = Interact / AI / Writeback 的职责边界。

# 1. 总体视觉方向

## 1.1 产品气质

产品应该像一个安静的研究员桌面，而不是互联网产品后台。所有设计感来自排版、层级、间距、细线、留白、字体、微交互，而不是来自高饱和颜色、巨大卡片、渐变和复杂装饰。

理想状态是：用户第一眼不会觉得“哇，好有设计感”，而是会觉得“这里的信息很有秩序，而且很适合长期使用”。

## 1.2 明确禁止

禁止高饱和蓝、紫色渐变、彩虹分类、玻璃拟态、重阴影、大圆角、巨型 Hero、emoji 导航、过多 icon、过多按钮、过多独立 Card、默认 Streamlit Widget 视觉、页面之间完全不同的 UI 风格。

禁止为了制造科技感使用深色终端风、霓虹色、荧光边框、发光效果。

禁止把产品做成 Notion、Linear、ChatGPT Dashboard、传统券商终端、BI Dashboard 或 SaaS Admin Panel 的视觉复制品。

# 2. 信息架构：从 Sidebar + Page 升级为 Workspace

```text
├────────────────┬────────────────────────────────────────────────────────────┤
│                │                                                            │
│ WORKSPACE      │                                                            │
│                │                     MAIN WORKSPACE                         │
│  Library       │                                                            │
│  Radar         │                                                            │
│  Review        │                                                            │
│  Battle        │                                                            │
│  Archive       │                                                            │
```

### 2.1 Sidebar

宽度默认 224–232px。必须支持 Collapse。展开态显示文字，折叠态显示低干扰 icon / 缩写，不得把大量内容压缩到 64px 后变成图标墙。

Sidebar 分为三组：

```text

  Library
  Radar
  Review
  Battle
  Archive

KNOWLEDGE
  01 行业认知               06
  02 项目解剖               31
```

API 设置不能长期占据 Sidebar。改成底部 Settings → Drawer / Modal。大多数浏览时间里 Sidebar 不应该被 API 厂家、模型、Base URL、Key 等配置污染。

### 2.2 Header

Header 高度控制在 56–60px，结构极轻。

```text
┌─────────────────────────────────────────────────────────────────────────────┐
│ 一级投研知识库      [  Search anything...   Ctrl K   ]          ● Indexed  │
└─────────────────────────────────────────────────────────────────────────────┘
```

左侧保留产品名称；中间为全局搜索入口；右侧只保留系统状态、设置等低权重信息。不要再采用“标题 + 搜索框 + 搜索按钮”的传统网页表单结构。

设计原则：颜色必须低饱和；Accent 只用于 active、focus、primary action、重要链接和少量信息强调；9 个分类不再使用 tab10 等高辨识度色板。

字号参考：页面标题 28–32px；Section 16–18px；正文 16–17px；辅助信息 12–13px；Meta 11–12px。正文行高 1.85–2.0。

# 6. Document Reader：全站最高优先级

阅读页是整个产品最重要的页面。必须优先确保大段中文文本、表格、引用、技术内容和长时间滚动的舒适度。

采用三栏 Reading Workspace：Context Rail + Reading Column + TOC。

```text
┌───────────────┬───────────────────────────────────────┬──────────────────────┐
│ DOCUMENT      │                                       │ CONTENTS             │
│ CONTEXT       │           READING COLUMN              │                      │
│               │                                       │ 01 概览              │
│ 项目解剖      │ 伏塔_AI驱动电池研发平台                │ 02 市场              │
│               │                                       │ 03 投资逻辑          │
│ Track          │ 项目解剖 · 光计算 · 推进中             │ 04 风险              │
│ 光计算         │                                       │                      │
│ Status         │ ───────────────────────────────       │                      │
│ 推进中         │                                       │                      │
│ Updated        │ 正文正文正文正文正文…                 │                      │
│ 08-20          │                                       │                      │
│               │ 正文正文正文正文正文…                  │                      │
│ RELATED        │                                       │                      │
│ 光本位         │ ───────────────────────────────       │                      │
│ 行业总文档     │ 上一篇                             下一篇│                      │
│               │                                       │                      │

│ Start Battle   │                                       │                      │
```

正文宽度建议 720–800px。不要把正文塞进白色 Card，不要让正文左右出现过粗的边框。背景直接使用全局背景色或极浅 Surface。

正文标题采用 Editorial Heading；Meta 信息放在标题下方；正文采用 Noto Serif SC；表格、代码、技术数据可以切换到 Sans / Mono。

### 6.1 Reading Mode

提供 Zen Reading Mode：隐藏 Sidebar、Context Rail、TOC，只保留标题和正文。

可提供字号、行高设置；不要把这些控件做成永久浮动的控制面板，而是放进非常轻的阅读设置菜单。

提供阅读进度条，但必须非常细，不能成为装饰性元素。

### 6.2 TOC

TOC 默认只展示 h2。h3 在当前章节展开时出现。当前章节用深色文字 + 1px Accent 左线表示，不使用明显色块。

### 6.3 Context Rail

左侧 Context Rail 负责回答“我现在在哪里”。包括分类、Track、Status、Updated、Related Documents 和 Actions。

它不是原来的 Sidebar，而是当前文档的上下文面板。

# 9. Thesis Battle

Battle 必须从“AI Chat”升级成“Investment Thesis Stress Test”。

```text
┌───────────────┬───────────────────────────────────────────┬───────────────────┐
│ THESIS        │ BATTLE ROOM                              │ BATTLE STATE      │
│ CONTEXT       │                                           │                   │
│               │ ROUND 03 · ASSUMPTION ATTACK              │ Core Assumptions  │
│ 项目：伏塔     │                                           │ 01 TAM             │
│ 核心观点       │ AI                                      │ 02 Pricing         │
│ …             │ 你的假设依赖……                           │ 03 Customer        │
│               │                                           │                   │
│ Evidence      │ YOU                                     │ Unresolved         │
│ …             │ 我的证据是……                              │ 02 questions       │
│               │                                           │                   │
│ Assumptions   │ ─────────────────────────────────────── │ Falsification      │
│ …             │                                           │ …                 │
│               │ [ Start next attack ]                     │ Confidence         │
│               │                                           │ Medium             │
└───────────────┴───────────────────────────────────────────┴───────────────────┘
```

Battle 流程建议固定阶段：

```text
01 Assumption Attack
        ↓
02 Evidence Challenge
        ↓
03 Counterexample
        ↓
04 Falsification Condition
        ↓
05 IC Summary
```

聊天气泡不应成为主视觉。AI 和用户消息应更像研究记录。每轮必须明确当前攻击阶段。

Writeback Preview 不放在对话上方，而是改成右侧 Review Drawer：

```text
┌────────────────────────────────────┐
│ REVIEW PENDING                     │
│                                    │
│ Changes to write back              │
│                                    │
│ + 新增：客户验证                    │
│ ~ 修改：核心假设                    │
│ - 删除：旧判断                      │
│                                    │
│ [ Edit ]      [ Reject ] [ Approve ]│
└────────────────────────────────────┘
```

保留“预览 → 人工审批 → 写回”的工程约束。


用户不应该同时面对“上传、AI 分析、分类、入库、结果、下一步评审”等大量 UI。必须让工作流天然呈现为四个阶段。

# 15. 状态体系

所有页面统一：Empty / Loading / Error / Success / Warning / Interrupted / Pending Approval。

Empty State 示例：

```text
No Battle history yet
Start a Battle from any project document.

[ Start Battle ]
```

Error 示例：

```text
Something went wrong.
Your source files are safe. You can retry the task.

[ Retry ]
```

禁止依赖 Streamlit 默认 st.info / warning / error 的原生视觉。

---

# 16. 交互原则

第一原则：整行可点击。第二原则：Primary action 只有一个。第三原则：次级动作通过 Quiet Button / Context Menu / Drawer 暴露。第四原则：操作结果必须明确反馈。第五原则：长任务必须显示状态，不能让用户猜测。第六原则：可撤销的动作尽量提供 Undo。第七原则：写回知识库必须始终拥有人工审批节点。

Hover 反馈采用极轻背景变化。点击反馈采用 150–220ms transition。不要使用 bounce、overshoot、强 scale 或复杂动画。

---

# 17. Keyboard Interaction

至少实现：

```text
Ctrl / Cmd + K      Command Palette
Ctrl / Cmd + P      Open recent / document navigation
Esc                 Close drawer / modal / palette
J / K               Next / previous document（可选）
O                   Open current document
B                   Start Battle（可选）
R                   Start Review（可选）
```

快捷键必须是渐进增强，不得破坏普通输入框行为。

# 18. 响应式

```text
> 1200px   Full Workspace
900–1200px Sidebar auto-collapse
< 900px    Sidebar → Drawer
< 760px    Reading mode becomes single-column
```

不要简单地把桌面布局压成手机的一列。阅读页必须优先保证正文宽度、字号和操作可达性。

# 19. Static Site / Streamlit 一致性

两套前端必须共享同一套视觉系统：

```text
             ┌─────────────────────┐
             │   Design Tokens     │
             └─────────┬───────────┘
                       │
             ┌─────────┴───────────┐
             │                     │
      Static Read Mode      Interactive Mode
      build_html.py         app.py / modules
             │                     │
       Browse / Search        AI / Writeback
       Read / Context         Review / Battle
             │                     │
             └─────────┬───────────┘
                       │
                Same visual language
```

Static Site 应该像 Interactive Site 的“只读模式”，而不是另一个网站。

# 22. 最终判断标准

完成后，请用以下问题检查 UI，而不是问“看起来是否更漂亮”：

1. 用户能否在 3 秒内知道当前所在位置？
2. 用户能否在 5 秒内找到一篇最近阅读过的文档？
3. 文档阅读 30 分钟后是否仍然舒服？
4. 页面是否存在过多卡片、按钮、颜色和视觉噪音？
5. 用户是否能明确理解 AI 当前在做什么？
6. 所有写回动作是否都有明确的审批边界？
7. Static 与 Streamlit 是否像同一个产品？
8. Sidebar 是否会因为文档数量增长而失控？
9. 用户是否需要大量鼠标点击才能完成搜索、打开文档和发起研究动作？
10. 任何页面是否出现了“为了设计而设计”的视觉元素？

最终目标不是“一个漂亮的知识库网站”。

最终目标是：

```text
                    PERSONAL RESEARCH OS

        Search ────────┐
        Library ───────┤
        Reader ────────┤
        Radar ─────────┤
        Review ────────┼────→  Investment Thinking
        Battle ────────┤
        Archive ───────┤
        Context ───────┘
```

一句话定义：**让信息安静地存在，让研究动作自然发生，让投资判断成为界面的最终中心。**
