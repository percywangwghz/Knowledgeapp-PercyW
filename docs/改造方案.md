## 〇、现状诊断（已核实，含文件:行号）

### 1. 上传与 PDF 处理
- "上传接口"不是 HTTP API，是 Streamlit 页面：`ingest.py:357` 的 `st.file_uploader`，多选文件一次性全读进内存（`ingest.py:362`），后台单线程串行处理，模块级单例任务锁，并发提交被静默丢弃（`ingest.py:307-308`）。
- PDF 转文本在 `ingest.py:73-76`：pypdf 逐页抽文字层、换行拼接，**不产出 Markdown**——图表全丢、表格退化成无结构文字流、标题/版面/公式全丢、扫描件无 OCR 直接报错。
- token/上下文损失三处硬截断：`ingest.py:29` 分类只看前 3000 字；`ingest.py:28,215` 整理只送前 15000 字且留存原文同样截断；`ingest.py:170` 输出上限 8000 token。叠加 `organize_document` 有损改写，入库 .md 与原文差距大。

### 2. 雷达搜索的 Kimi 原生依赖
- 硬依赖点：`llm.py:135` 的 `$web_search` builtin_function——搜索在 Moonshot 服务端执行，客户端无真实搜索能力。调用方仅两处：`radar_auto.py:302`、`radar_wechat.py:231`。
- 伴生耦合：`llm.py:244-245` `thinking` 字段、k2.6 只允许 temperature=1（`llm.py:221`）、`reasoning_content` 回传（`llm.py:190-193`）、prompt 明文写"请用 `$web_search`"（`radar_auto.py:91-117`）。
- 数据流（JSON 落盘 + radar.py 看板）与 LLM 层解耦良好，改造只需动 llm.py 和两个调用点。

### 3. 模型写死 + Kimi 品牌耦合
- 根源：`llm.py:34` `DEFAULT_MODEL = os.environ.get("MOONSHOT_MODEL", "kimi-k2.6")`，所有调用方吃默认值。
- 环境变量全是 `MOONSHOT_*` 命名；`get_api_key()` 末级回退读 `~/.kimi/config.toml`（`llm.py:71-86,124`）。
- `llm.py:38` `PRICING` 只认 kimi-k2.6，换模型计费会出问题。

### 4. 调研结论（v5 最终）

一个重要认知：**官方 skill 的本质 = "官方 CLI/API + SKILL.md 说明书"**。Streamlit app 集成的是 skill 背后的 CLI/API（执行体），SKILL.md 随包分发供有 agent 环境的用户直接使用。

**PDF → Markdown（v5 定调）：放弃一切第三方解析服务（含 MinerU 云端），解析质量只挂钩用户自己的模型 API**

- v5 决策：VLM 主力档走用户注入的 OpenAI 兼容多模态 API（本地渲染页图 → 用户的模型转 Markdown），本地库链（pymupdf4llm/pdfplumber/pypdf）保底。质量、成本、数据流向全部归属用户自己选的厂家。
- 调研备忘（不采用但留档）：MinerU 官方 skill（OpenDataLab，`MinerU-Ecosystem/skills`，Apache 2.0，flash 免 key/precision 配 token）曾是首选，因用户要求"数据不出自己 API 边界"而放弃；anthropics 官方 pdf skill 的本地配方（pdfplumber 抽表、pytesseract OCR）已吸收进本地链。

**联网搜索（v5 定调）：复用 LLM 厂家原生搜索能力，无独立搜索 API、无备轨**

- 主流厂家自带联网搜索（已核实，2026-08）：国内 Moonshot `$web_search`、智谱 `web_search`、豆包/火山方舟联网插件、阿里通义 `enable_search`；国际 OpenAI `web_search`、Gemini grounding、Anthropic `web_search` 工具、xAI Live Search、Perplexity 全模型内置。DeepSeek 无服务端搜索，是少数派。完整矩阵见方案二 2.1。
- 结论：雷达无需引入任何独立搜索服务，按厂家注入原生搜索参数即可；厂家无搜索能力时直接报错提示。
- 调研备忘（不采用但留档）：独立搜索 API（Tavily/Exa/Brave/博查等官方 skill/API）与"先搜后答两段式"曾是备轨方案，因用户决策"单轨 + 无搜索能力即报错"而放弃。

## 方案一：PDF 预处理（VLM 走用户自己的 API 为主力，本地库链保底，无第三方服务）

**架构定调（v5，用户最终决策）**：**完全放弃 MinerU 及一切第三方解析服务**。PDF 解析质量只挂钩用户自己配置的 API——主力档走用户注入的多模态模型（VLM），本地库链作无视觉模型时的保底。数据只流向用户自己选的 API 厂家（用户自己的账号），纯本地档则哪都不去。

### 1.1 新增 `skills/pdf-preprocess/`
```
skills/pdf-preprocess/
├── SKILL.md    # 自写（Kimi Code/Agent Skills 通用格式）：PDF→Markdown 工作流与降级策略说明
└── convert.py  # 自研编排层，统一入口：python convert.py <file> → stdout 输出 md
```
`convert.py` 内部**多级回滚链**（按可用性自动探测，逐块粒度生效，见 1.3）：
1. **VLM 主力档**：本地 pymupdf 把 PDF 逐块渲染成图片（纯本地渲染）→ 走方案三注入的 OpenAI 兼容 API 发给用户配置的多模态模型 → 逐块转 Markdown。质量完全取决于用户自己的厂家/模型选择；扫描件、图表解读、复杂版面、公式全部覆盖——这正是本地库链的死穴。
2. **pymupdf4llm**（本地保底主力）：标题层级、Markdown 表格、页锚点；
3. **pdfplumber**（本地补强）：`extract_tables()` 修正表格抽取；
4. **pypdf 兜底**（现有逻辑，裸环境保证可用）。

配套要求：
- **多模态 only**：PDF VLM 档要求配置的主模型具备视觉能力（如 kimi-k2.6-vision / qwen-vl-max / glm-4v / gpt-4o 等），文档和 README 显著标注"PDF 高保真解析需配置多模态模型"；不提供独立的解析模型选项——检测到主模型不支持视觉时直接落本地库档并在 UI 说明原因。
- **进度可见**：VLM 档逐块转换时 UI 显示进度条（当前块/总块数、当前页码范围、已用时），失败块在进度条旁实时标注；解析成本随页数线性增长这一点写进文档说明，不做前置确认拦截。

### 1.2 ingest.py 接入点
- `extract_text`（`ingest.py:61`）PDF 分支 → `convert.py`，走 1.1 的回滚链；任一档不可用自动降级，不阻断入库。
- docx 分支顺带修复：按文档顺序输出段落+表格（现状段落全在前、表格堆在最后，`ingest.py:78-84`）。

### 1.3 大 PDF 处理：本地切分 + 多级回滚

- **切分（纯本地，零新依赖）**：两遍走——先 pypdf 廉价抽文字层定位目录/标题边界，**按语义边界（章节起始页）切**，避免砍断跨页表格和长段落；切分工具链 pymupdf → pypdf → qpdf 兜底。VLM 档每块控制在模型上下文与单次图片数量限制内（块大小可配）。
- **逐块转换（部分降级）**：每块独立走 1.1 的回滚链；单块失败/超时只影响该块（如 VLM 调用失败仅该块落本地链），整篇不失败。失败块记页码范围，UI 标注"第 x-y 页低保真提取"并支持单独重试；VLM 档多块**串行 + 指数退避**（遵守用户 API 的 RPM 限制），不并行。
- **合并**：各块 Markdown 顺序拼接，块首注入页码锚点注释（`<!-- p.41-60 -->`），既保留溯源，也作为 1.4 分段整理的天然切点；临时切块文件转换完即删，仅失败块保留供重试。

### 1.4 消除 token/上下文损失
- VLM 档直接产出结构化 Markdown（表格/标题/图表文字解读），从根上解决 pypdf 纯文本流的信息丢失；本地档靠 pymupdf4llm 的结构化输出同样远优于纯文本流。
- 取消 `TEXT_LIMIT=15000` 硬截断，改分段整理（map-reduce）：按 Markdown 标题切块 → 每块 `organize_document` → 合并；`CLASSIFY_TEXT_LIMIT` 改 env 可配。
- 入库 .md 末尾附原文折叠段（或同目录 `*.raw.md`），改判分类重整有全文可用。

### 1.5 上传体验修补（顺带小改）
- 文件逐个读入+落临时盘；任务被占用时显式提示（现状静默丢弃）；失败记录具体原因；改判分类后的重整移入后台线程。

### 1.6 依赖
- 默认新增：`pymupdf4llm`（本地主力 + 页面渲染）、`pdfplumber`（表格补强）。无其他新增服务或重型依赖。
- VLM 档零新增依赖：复用 llm.py 的 OpenAI 兼容调用，仅请求体带 base64 图片（需确认目标厂家 vision 接口的消息格式差异，适配层写在 convert.py 内）。

### 1.7 v6 增补（2026-08-13，均已实施）

- **提速（简历解析软件同款逻辑）**：文本层分流——切块后按块均字符/页（`KB_TEXT_LAYER_MIN`，默认 100）判定，有文本层的块直接本地解析不发 VLM 请求；仅扫描/图片块走 VLM，且 VLM 块 `ThreadPoolExecutor` 并发（`KB_VLM_WORKERS` 默认 3）。原生电子版研报基本不再触发 VLM，分钟级 → 秒级。
- **进度改"预计剩余"**：删除"本块已用时"；信息条与每文件明细均显示「预计剩余约 X 分钟」（PDF 按块粒度、其余按文件粒度，`state["blocks"]` 落盘供前端 `_live_eta`）。
- **中断可恢复**：点"开始分析"时文件字节缓存 `data/tmp_upload/`、点"确认入库"时计划落盘 `data/ingest_save_plan.json`；重启后中断提示下提供「🔄 重新发起」「🗑 清除记录」按钮；正常完成自动清缓存。
- **重要图表自动截取**：转换时纯本地截取（嵌入位图 bbox 面积阈值 + 矢量图区整页截图，md5 去重，`KB_IMG_MAX` 默认 20 张/文档、0 关闭）；分析时暂存 `data/tmp_imgs/`，入库搬进 `knowledge/assets/img/<文档名>/`，md 正文末尾（折叠段之前）追加「## 📷 重要图表（自动截取）」相对路径引用。公众号雷达产出的是信号 JSON 不是 md，不在本功能范围。
- **归档页定版 UI**：外大框包拖入区+输出区；输出区定高 560px 常驻占位、内容滚动、打字机流式回显。

## 方案二：雷达搜索去 Kimi 化（单轨：复用各厂家原生搜索能力）

**架构定调（v5 用户决策）**：主流 LLM 厂家大多自带联网搜索（OpenAI `web_search`、Gemini Google Search grounding、豆包/火山方舟 `web_search` 插件、智谱 `web_search`、Kimi `$web_search`），雷达保持"带搜索对话"的形态不变，只把搜索能力来源从"写死 Kimi"改为"按厂家注入原生搜索参数"。**无独立搜索 API、无备轨**：厂家不提供搜索能力时直接报错提示"该 API 厂家未提供搜索功能"。一把 key 全搞定，搜索费计在用户自己的模型账单里。

### 2.1 厂家原生搜索适配层（llm.py 内）
- `get_search_payload(model, base_url)` 改为直接读方案三的 `PROVIDERS` 预设表（厂家信息单一事实源，用户在 UI 选的就是识别结果，无需猜测）；custom 项按 base_url 域名 + 模型名前缀做尽力匹配，匹配不上视为无搜索能力。
- 厂家覆盖矩阵（"已核实"= 已查官方文档/可信来源确认能力存在；具体请求字段落地时逐家按官方文档核对）：

| Moonshot Kimi | ✅ | 已核实 | `tools=[{"type":"builtin_function","function":{"name":"$web_search"}}]`（现状平移） |
| 智谱 GLM | ✅ | 已核实 | `tools=[{"type":"web_search",...}]` |

### 2.2 调用点与报错
- `chat_with_search()`（`llm.py:216-287`）保留函数签名，内部改为：`get_search_payload()` 返回 None 时**抛出明确错误**"当前配置的 API 厂家（xxx）未提供联网搜索功能，雷达不可用"；否则注入对应参数发起请求。

- 移除 `~/.kimi/config.toml` 末级回退（或改为显式开关 `KB_READ_KIMI_CONFIG=1`，默认关）。

## 方案三：API 注入（key + 厂家 + 模型）

**为什么要注入 base_url**：换厂家就是换地址（`api.moonshot.cn` / `api.deepseek.com` / `dashscope.aliyuncs.com` / `api.openai.com` …），现状端点写死 Moonshot（`llm.py:32`），key 对了地址错了照样 401。但**不让用户手填 URL**——UI 用厂家下拉自动带出。

### 3.1 厂家预设表（config.py，数据驱动）
- 新增 `PROVIDERS` dict：每个厂家一条 `{base_url, default_model, vision, search}`（vision=是否多模态、search=原生搜索参数片段，直接供方案二的 `get_search_payload` 复用——厂家信息只有这一处事实源）：
  - 已核实 9 家：Kimi / 智谱 / 豆包(火山方舟) / 通义(DashScope) / OpenAI / Gemini / Anthropic / xAI / Perplexity；DeepSeek（标注无搜索、雷达报错用）；
  - 待核对 5 家（腾讯混元/MiniMax/阶跃/百度千帆/Mistral）落地时补；
  - `custom` 项：自定义 base_url + 模型，覆盖代理/中转站/新厂家。

### 3.2 llm.py 注入链泛化（镜像现有 key 链 `llm.py:109-124`）
```python
def set_thread_model(model): ...        # 镜像 set_thread_api_key
def register_model_provider(fn): ...    # 镜像 register_key_provider
def get_model():
    # 线程注入 → 前端 provider(session_state) → env KB_MODEL（兼容 MOONSHOT_MODEL）→ 厂家预设默认
```
- base_url 同理走注入链：`KB_BASE_URL`（兼容 `MOONSHOT_BASE_URL`）→ 厂家预设表查得，无需用户填。
- `chat()` 默认参数 `model=None` → 函数体 `model = model or get_model()`；调用方不动。

### 3.3 app.py 前端
- 设置区改为三个控件：**厂家下拉**（预设表 + 自定义）→ 自动带出 Base URL（自定义时才显示可编辑输入框）→ **模型**输入框（占位为厂家推荐模型）→ **API key** 输入框。持久化 `data/local_provider.txt` / `local_model.txt` / `local_base_url.txt`。
- 选 DeepSeek 等无搜索厂家时，雷达页提示"该厂家未提供搜索功能"；选纯文本模型时，PDF VLM 档落本地链并提示（多模态 only，README 显著标注）。
- 各后台线程启动处（`set_thread_api_key` 旁边）同步 `set_thread_model`。

### 3.4 收尾
- `PRICING` 查不到模型记 0 + warning；补常见模型价格。
- 雷达搜索随厂家原生能力走（方案二），无需单独配置搜索 key。

## 实施顺序建议（后续落地时）

1. **方案三**：注入泛化，改动最小，先行。
2. **方案二**：llm.py 加厂家原生搜索适配层（`get_search_payload`，数据驱动）→ `chat_with_search` 改走适配层 + 无搜索能力即明确报错 → prompt 去 `$web_search` 字样。
3. **方案一**：convert.py 本地库链（pymupdf4llm → pdfplumber → pypdf）→ 大 PDF 切分 → VLM 主力档（走用户注入 API，依赖方案三的解析模型字段）→ 分段整理 → UI 修补。
4. 每步更新已有测试（`test_ingest.py`/`test_radar_auto.py`），新增 search/convert 封装单测（mock subprocess/HTTP/LLM 响应）。

## 风险与注意

- VLM 档成本与速度：逐块调用多模态模型，花用户自己的 token，大 PDF 明显慢于本地链；UI 以进度条展示逐块进度与失败块（不做前置确认拦截），成本随页数线性增长写进文档。
- 主模型无视觉能力时 VLM 档不可用：多模态 only（文档显著标注），检测到不支持即落本地库档并在 UI 说明原因，不静默降质。
- 各厂家 vision 接口消息格式有差异（图片 base64 字段、单请求图片数上限），适配层集中在 convert.py，新增厂家只改一处。
- 各厂家原生搜索的格式/限额/计费规则不同（如 Gemini grounding 按查询计费、豆包联网插件需开通），适配表数据驱动，落地时逐家按官方文档核对；厂家无搜索能力（如 DeepSeek）时雷达直接报"该 API 厂家未提供搜索功能"并给推荐厂家列表。
- 原生搜索的结果不返回结构化 URL 列表时，信号的来源 URL 字段可能弱化（取决于厂家返回的引用信息），落地时逐家验收信号 JSON 的完整性。
